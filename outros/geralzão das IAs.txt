## 1. Introdução aos formatos text-based de serialização

### O que são formatos text-based?

- São formas de representar dados estruturados em texto legível por humanos, fáceis de transportar via rede, armazenar em disco e editar em qualquer editor de texto simples. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)
- A ideia é que, mesmo em outro sistema, linguagem ou arquitetura, o conteúdo possa ser lido e interpretado de forma confiável.

### Exemplos rápidos (sem detalhes ainda)

- **FWF (Fixed‑Width Format)**  
  ```text
  1234567890
  1111222233
  ```
  Cada coluna ocupa um número fixo de caracteres.

- **DSV: CSV, TSV**  
  ```csv
  name,age,city
  Alice,30,São Paulo
  Bob,25,Rio
  ```
  ```tsv
  name	age	city
  Alice	30	São Paulo
  Bob	    25	Rio
  ```

- **YAML**  
  ```yaml
  person:
    name: Alice
    age: 30
  ```  

- **JSON**  
  ```json
  {"person": {"name": "Alice", "age": 30}}
  ```  

- **XML**  
  ```xml
  <person>
    <name>Alice</name>
    <age>30</age>
  </person>
  ```  

- **TOML**  
  ```toml
  [person]
  name = "Alice"
  age  = 30
  ```  

### Usos mais corriqueiros

- **CSV/TSV**: arquivos de planilha, exportações de banco de dados, dados tabulares. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)
- **YAML**: configurações de aplicativos, CI/CD (GitHub Actions, GitLab CI), arquivos de configuração de bibliotecas. [elixirforum](https://elixirforum.com/t/data-serialization-formats/53818)
- **JSON**: APIs web, mensagens de rede, configurações simples, bancos de dados noSQL. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)
- **XML**: configurações complexas, documentos extensíveis (XHTML, SVG), SOAP, feeds (RSS/Atom). [sandfox](https://sandfox.me/misc/file-formats-misuse.html)
- **TOML**: configurações de projetos (Rust `Cargo.toml`, Python `pyproject.toml`, etc.). [mojoauth](https://mojoauth.com/parse-and-generate-formats/parse-and-generate-toml-with-r)
- **FWF**: arquivos de entrada de sistemas legados (mainframes, bancários, governamentais). [math.ucla](https://www.math.ucla.edu/~anderson/rw1001/library/base/html/read.fwf.html)

## 2. Dados estruturados vs. não estruturados

### Dados estruturados

- Seguem um **esquema** bem definido: colunas, tipos, hierarquia, campos nomeados. [mongodb](https://www.mongodb.com/resources/basics/unstructured-data/structured-vs-unstructured)
- Exemplos:  
  - CSV com colunas `id`, `name`, `age`.  
  - JSON com chaves fixas como `{"name": "...", "age": 30}`.  
- São fáceis de filtrar, agrupar e integrar em tabelas/bancos.

### Dados não estruturados

- Sem esquema pré‑definido: blocos de texto livre, arquivos de log, PDFs, e‑mails, etc. [imperva](https://www.imperva.com/learn/data-security/structured-and-unstructured-data/)
- Exemplo textual livre:
  ```text
  O paciente chegou às 14h com dor abdominal intensa...
  ```
- São mais flexíveis, mas precisam de etapas de pré‑processamento (extração, normalização) antes de análise.

### Semiestruturado

- Entre os dois: têm algum padrão (chaves, campos), mas podem variar entre registros. [ibm](https://www.ibm.com/think/topics/structured-vs-unstructured-data)
- JSON aninhado, XML com campos opcionais, YAML variável.

## 3. Serialização e desserialização

### O que é serialização?

- Conversão de objetos/estruturas em memória (listas, dataframes, structs) para um formato “plano” armazenável ou transmitível (JSON, XML, CSV, etc.). [dev](https://dev.to/anh_trntun_4732cf3d299/understanding-serialization-and-deserialization-methods-examples-and-best-practices-nm4)
- Uso típico: salvar resultados de modelos, enviar dados por HTTP, armazenar em arquivos de configuração.

### O que é desserialização?

- Transformação do formato “plano” de volta em objetos/estruturas na linguagem. [handbook.osc](https://handbook.osc.to/data_management/formats_serde/)
- Exemplo:  
  - Ler um arquivo JSON e montar um `list` ou `data.frame` em R.  
  - Ler um XML e gerar um objeto de metadados em Python.

### Por que isso importa?

- Permite intercâmbio entre diferentes linguagens e sistemas. [maddevs](https://maddevs.io/glossary/data-serialization/)
- Habilita reprodução de resultados, armazenamento de estado e interoperabilidade entre serviços.

## 4. Apresentação separada de cada formato

### FWF (Fixed‑Width)

- Cada campo tem um número fixo de caracteres; não há separadores. [gist.github](https://gist.github.com/badele/f2d4e74b9135c25a69834cacc3f89b87)
- Exemplo válido:
  ```text
  1234567890
  1111222233
  ```
  onde `id` = 3 caracteres, `name` = 7, `score` = 0.

- Exemplo mais legível:
  ```text
  001Alice   30
  002Bob     25
  ```

- Usos típicos: arquivos de sistemas legados, bancos de dados em formato “flat”, relatórios de mainframes. [rdrr](https://rdrr.io/cran/multifwf/man/read.multi.fwf.html)

### DSV (CSV / TSV)

- **CSV**: campos separados por vírgulas, uma linha por registro. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)
  ```csv
  id,name,age
  1,Alice,30
  2,Bob,25
  ```

- **TSV**: campos separados por tabulações; útil quando os dados contêm vírgulas. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)
  ```tsv
  id	name	age	address
  1	Alice	30	São Paulo
  2	Bob	    25	Rio
  ```

- Usos típicos: exportação de bancos de dados, planilhas, arquivos de dados de estatística. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)

### YAML

- Formato hierárquico, baseado em indentação, com ênfase em legibilidade humana. [elixirforum](https://elixirforum.com/t/data-serialization-formats/53818)
  ```yaml
  person:
    name: Alice
    age: 30
    contacts:
      - type: email
        value: alice@example.com
  ```

- Usos típicos: configuração de apps, CI/CD, metadados de documentos. [elixirforum](https://elixirforum.com/t/data-serialization-formats/53818)

### JSON

- Formato de pares chave‑valor, com objetos e arrays, muito usado na web. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)
  ```json
  {
    "person": {
      "name": "Alice",
      "age": 30,
      "contacts": [
        {"type": "email", "value": "alice@example.com"}
      ]
    }
  }
  ```

- Usos típicos: APIs REST, mensagens de microserviços, configurações simples. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)

### XML

- Formato baseado em tags, com namespaces e capacidade de extensão. [sandfox](https://sandfox.me/misc/file-formats-misuse.html)
  ```xml
  <person>
    <name>Alice</name>
    <age>30</age>
    <contacts>
      <contact type="email">alice@example.com</contact>
    </contacts>
  </person>
  ```

- Usos típicos: documentos XML, configurações complexas, SOAP, RSS/Atom. [sandfox](https://sandfox.me/misc/file-formats-misuse.html)

### TOML

- Formato de chave‑valor nomeado por tabelas (`[section]`), pensado para configurações. [mojoauth](https://mojoauth.com/parse-and-generate-formats/parse-and-generate-toml-with-r)
  ```toml
  [person]
  name = "Alice"
  age  = 30

  [[person.contacts]]
  type  = "email"
  value = "alice@example.com"
  ```

- Usos típicos: configurações de projetos (Rust, Python, etc.). [mojoauth](https://mojoauth.com/parse-and-generate-formats/parse-and-generate-toml-with-r)

## 5. Diferenças sutis entre formatos parecidos

### JSON vs. YAML

- JSON é mais rígido: não admite comentários, exige aspas, suporte mais limitado a tipos complexos. [sandfox](https://sandfox.me/misc/file-formats-misuse.html)
- YAML é mais “flexível” e legível, mas a sintaxe de indentação pode gerar erros difíceis de debugar. [elixirforum](https://elixirforum.com/t/data-serialization-formats/53818)

### JSON vs. TOML

- JSON representa estruturas aninhadas com objetos e arrays; TOML organiza por tabelas e sub‑tabelas. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)
- TOML é mais intuitivo para configurações simples, mas JSON é mais universal em APIs. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)

### XML vs. JSON / YAML

- XML é mais verboso, mas permite namespaces e extensibilidade complexa. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)
- JSON/YAML são mais concisos e fáceis de ler em logs, mas menos flexíveis para documentos mistos. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)

### CSV vs. FWF

- CSV usa separadores e pode ter campos com aspas quando contêm o separador; FWF é totalmente baseado em posições. [beeceptor](https://beeceptor.com/docs/concepts/data-exchange-formats/)
- FWF é mais robusto em sistemas legados, mas difícil de inspecionar visualmente sem conhecer a especificação de larguras. [math.ucla](https://www.math.ucla.edu/~anderson/rw1001/library/base/html/read.fwf.html)

## 6. Tropeços e problemas mais comuns

### FWF

- Erro: largura de coluna errada (por exemplo, uma linha com espaços extras ou faltando).  
  ```text
  001 Alice 30
  002Bob     25
  ```
  Leitura quebra porque o parser espera posições fixas.

- Problemas típicos:  
  - Caracteres de controle (tab, quebra de linha) no meio da linha.  
  - Excesso de espaços ou campos justificados à direita/à esquerda não documentados.

### CSV / TSV

- Erro: campos com separador dentro do valor e sem aspas:
  ```csv
  1,Alice,30,São Paulo,Brasil
  2,Bob,25,"São Paulo, Boa Viagem",Brasil
  3,Charlie,40,"São Paulo, "'"Brasil
  ```
  A última linha pode gerar erro se o parser não tratar aspas corretamente.

- Problemas típicos:  
  - Diferentes separadores entre arquivos (`,` vs `;` vs `\t`).  
  - Códigos de barramento (CR, LF) variando entre sistemas.  
  - Campos com aspas duplas mal escapadas.

### YAML

- Erro: indentação inconsistente:
  ```yaml
  person:
    name: Alice
   age: 30  # um espaço a menos
  ```
  vira erro de estrutura.

- Problemas típicos:  
  - Espaços/tab misturados que “dão azar” em editors diferentes.  
  - Tipos inferidos de forma inesperada (por exemplo, `on`/`off` lidos como booleanos).

### JSON

- Erro: vírgula à direita ou falta de aspas:
  ```json
  {
    "name": Alice,
    "age": 30,
  }
  ```
  Nenhum parser JSON aceita isso.

- Problemas típicos:  
  - Uso de comentários (`//`), que não são parte da especificação.  
  - Quebras de linha dentro de string sem escape.

### XML

- Erro: tag não fechada ou mal balanceada:
  ```xml
  <person>
    <name>Alice</name>
    <age>30
  </person>
  ```
  Erro de parsing.

- Problemas típicos:  
  - Uso de caracteres especiais (`<>&`, etc.) sem escapar.  
  - Espaços e quebras em acentos não tratados com encoding correto.

### TOML

- Erro: chave fora de tabela ou sintaxe de array malformada:
  ```toml
  [person]
  name = "Alice"
  age  = 30
  [person]  # duplicado
  ```
  ou
  ```toml
  contacts = ["email", "phone,"
  ```
  quebra o parser.

- Problemas típicos:  
  - Uso de regras não suportadas (ex.: versão 0.5 vs 1.0).  
  - Duplicação de tabelas com semântica ambígua.

## 7. Bibliotecas no R que trabalham com esses formatos

- **FWF**:  
  - `base::read.fwf()` (pacote padrão `utils`). [rdocumentation](https://www.rdocumentation.org/packages/utils/versions/3.6.2/topics/read.fwf)
  - `multifwf::read.multi.fwf()` para arquivos com múltiplos tipos de registro. [rdrr](https://rdrr.io/cran/multifwf/man/read.multi.fwf.html)

- **CSV / TSV**:  
  - `utils::read.csv()` / `read.csv2()` / `read.delim()` (base R).  
  - `readr::read_csv()` / `read_tsv()` (mais rápido e moderno). [stackoverflow](https://stackoverflow.com/questions/50454735/reading-tsv-files-from-different-folders-into-r-environment-and-adding-a-column)

- **YAML**:  
  - `yaml::read_yaml()` e `yaml::write_yaml()` (interface para `libyaml`). [github](https://github.com/r-lib/yaml/)

- **JSON**:  
  - `jsonlite::read_json()` / `write_json()` (mais simples e razoável inferência de tipos). [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)
  - `RJSONIO` (mais antigo, mas ainda usado).  

- **XML**:  
  - `xml2` ou `XML` para leitura, escrita e manipulação de XML. [conv4](https://conv4.me/blog/articles/data-format-comparison-guide)

- **TOML**:  
  - `toml::parse_toml()` e `toml::write_toml()`. [mojoauth](https://mojoauth.com/parse-and-generate-formats/parse-and-generate-toml-with-r)
  - `configr` (suporte a TOML, JSON, YAML, INI para configurações). [cran.r-project](https://cran.r-project.org/web/packages/configr/readme/README.html)

## 8. Ferramentas no Linux para trabalhar com cada formato

- **FWF**:  
  - `cut -c` para extrair campos por posição:
    ```bash
    cut -c1-3,4-10,11- file.fwf
    ```
  - `awk` para campos fixos com lógica mais complexa.

- **CSV / TSV**:  
  - `awk`, `cut`, `sort`, `grep` para manipulação tabular simples.  
  - `csvkit` (Python) para conversão, filtragem e inspeção de CSV/TSV. [github](https://github.com/dbohdan/structured-text-tools)
  - `xsv` (Rust) para operações rápidas em CSV. [github](https://github.com/dbohdan/structured-text-tools)

- **JSON**:  
  - `jq` (leitura, filtragem, extração de campos). [x-cmd](https://www.x-cmd.com/pkg/dasel/)
  - `dasel` ou `yq` para mesclar uso com YAML/TOML/XML. [x-cmd](https://www.x-cmd.com/pkg/dasel/)

- **YAML**:  
  - `yq` (similar ao `jq`, mas para YAML). [github](https://github.com/dbohdan/structured-text-tools)
  - `dasel` para manipular YAML, JSON, TOML, etc., em linha de comando. [x-cmd](https://www.x-cmd.com/pkg/dasel/)

- **XML**:  
  - `xmlstarlet` (consulta, edição, transformação de XML). [github](https://github.com/dbohdan/structured-text-tools)
  - `xsltproc` para transformações XSLT.  

- **TOML**:  
  - `dasel` ou `tomlq` para consultas e manipulação. [x-cmd](https://www.x-cmd.com/pkg/dasel/)

## Introdução

Formatos text-based de serialização representam dados estruturados em texto legível por humanos, para armazenamento, troca entre sistemas e APIs.

Exemplos de formatos:
- **FWF**: largura de campo fixa.

- **CSV/TSV**: planilhas, exportação de bancos de dados.

- **TOML**: configurações de projetos (Rust, Python).

## Dados estruturados vs. não estruturados

**Estruturados**:  
- Esquema pré‑definido (colunas, tipos, hierarquia).  
- Ex.: CSV, JSON, XML.

**Não estruturados**:  
- Texto livre, logs, correspondências, PDFs.  
- Ex.:
  ```text
  O paciente chegou às 14h com dor abdominal intensa.
  ```

**Semi-estruturados**:  
- Estrutura parcial (chaves, campos, mas variáveis entre registros).  
- Ex.: JSON aninhado, XML com campos opcionais.

---

## O que é serialização e desserialização?

- **Serializar**: transformar objetos/estruturas em memória em um formato “plano” (ex.: JSON, XML, CSV).  
- **Desserializar**: recuperar esses objetos a partir do formato plano.

Exemplo em R:

```r
library(jsonlite)

# objeto em memória
dados <- list(
  pessoa = list(
    nome = "Alice",
    idade = 30
  )
)

# serialização para JSON
json_str <- toJSON(dados, auto_unbox = TRUE)
cat(json_str, "\n")

# desserialização
lido <- fromJSON(json_str)
str(lido)
```

## Fixed‑Width Format (FWF)

Campos de largura fixa, sem separadores visíveis.

Arquivo exemplo (`pessoa.fwf`):
```text
001Alice   30
002Bob     25
```

Leitura em R:

```r
# criar arquivo fictício
writeLines(c(
  "001Alice   30",
  "002Bob     25"
), con = "pessoa.fwf")

# ler FWF: colunas de 3 (id), 7 (nome), 2 (idade)
dados_fwf <- read.fwf(
  "pessoa.fwf",
  widths = c(3, 7, 2),
  col.names = c("id", "nome", "idade")
)

dados_fwf
```

Escrita FWF (manual, pois não existe função padrão `write.fwf` simples):

```r
fmt <- function(id, nome, idade) {
  sprintf("%03d%-7s%02d", id, nome, idade)
}

cat(
  fmt(1, "Alice", 30),
  fmt(2, "Bob",   25),
  sep = "\n"
)
```

## Diferenças sutis entre formatos

- **JSON vs YAML**:  
  - JSON é rígido, não aceita comentários, exige aspas.  
  - YAML é flexível e legível, mas depende de indentação correta.

- **JSON vs TOML**:  
  - JSON: estruturas aninhadas com objetos e arrays.  
  - TOML: organiza por tabelas `[section]`, mais intuitivo para configurações simples.

- **CSV vs FWF**:  
  - CSV: separadores e aspas quando necessário.  
  - FWF: campos por posição, sem separadores visíveis.

- **XML vs JSON/YAML**:  
  - XML: muito verboso, mas com namespaces e extensibilidade.  
  - JSON/YAML: mais leves e fáceis de ler em logs.

### FWF

Arquivo com erro de largura (`pessoa_error_fwf.txt`):

### CSV

Arquivo com erro de aspas (`pessoa_error_csv.csv`):

Indentação inconsistente:

  nome: Alice

### JSON

Sem aspas na chave:

  name: "Alice",

```markdown
# Formatos Text-Based de Serialização de Dados

## Uma visão prática para análise e engenharia de dados

---

## 1. Introdução

### Dados textuais estruturados x não estruturados

- **Não estruturados**: texto livre, logs, artigos, conversas (ex: "João tem 30 anos e mora em SP")
- **Estruturados**: seguem regras de organização explícitas

### Exemplos breves de formatos estruturados

- **FWF** (Fixed Width Fields): `Nome      Idade Cidade    `
- **DSV** (CSV, TSV): `Nome,Idade,Cidade` → `João,30,SP`
- **YAML**: `nome: João\nidade: 30`
- **JSON**: `{"nome": "João", "idade": 30}`
- **XML**: `<pessoa><nome>João</nome><idade>30</idade></pessoa>`
- **TOML**: `nome = "João"\nidade = 30`

### Onde aparecem no dia a dia

- **FWF**: arquivos legados de sistemas bancários, recibos de cartão
- **CSV/TSV**: Excel, Google Sheets, dados abertos governamentais
- **YAML**: Docker Compose, Kubernetes, CI/CD (GitHub Actions)
- **JSON**: APIs REST, NoSQL (MongoDB), logs estruturados
- **XML**: DOCX, XLSX, SOAP, arquivos de nota fiscal
- **TOML**: `Cargo.toml` (Rust), `pyproject.toml` (Python)

---

## 2. Serialização e Desserialização

### Definição

- **Serialização**: transformar estruturas de dados (listas, data.frames, dicionários) em texto (ou bytes) para armazenamento/transmissão
- **Desserialização**: o processo inverso — reconstruir a estrutura a partir do texto

### Por que serializar?

- Salvar dados em arquivo
- Enviar via rede/API
- Compatibilidade entre linguagens

---

## 3. Os formatos em detalhe

### FWF (Fixed Width File)

```
001João       30SP        
002Maria      25RJ        
```

- Cada campo ocuma **número fixo de caracteres**
- Rápido para leitura em baixo nível
- **Problema comum**: espaços extras/truncamento

---

### DSV (Delimiter-Separated Values) - CSV/TSV

```csv
nome,idade,cidade
João,30,São Paulo
Maria,25,Rio de Janeiro
```

- Mais comum em análise de dados
- **Tropeço**: vírgula dentro do campo, encoding, cabeçalho ausente

---

### JSON

```json
[
  {"nome": "João", "idade": 30, "cidade": "São Paulo"},
  {"nome": "Maria", "idade": 25, "cidade": "Rio de Janeiro"}
]
```

- Universal para APIs
- **Tropeço**: vírgula extra, falta de aspas em chaves, sem suporte a comentários

---

### YAML

```yaml
pessoas:
  - nome: João
    idade: 30
    cidade: São Paulo
  - nome: Maria
    idade: 25
    cidade: Rio de Janeiro
```

- Legível para humanos
- **Tropeço**: problemas com indentação (misturar tabs/espaços)

---

### XML

```xml
<pessoas>
  <pessoa>
    <nome>João</nome>
    <idade>30</idade>
    <cidade>São Paulo</cidade>
  </pessoa>
  <pessoa>
    <nome>Maria</nome>
    <idade>25</idade>
    <cidade>Rio de Janeiro</cidade>
  </pessoa>
</pessoas>
```

- Verboso, com hierarquia clara
- **Tropeço**: tags não fechadas, falta de escapamento (`&`, `<`, `>`)

---

### TOML

```toml
[pessoas]
  [pessoas.joao]
  nome = "João"
  idade = 30
  cidade = "São Paulo"

  [pessoas.maria]
  nome = "Maria"
  idade = 25
  cidade = "Rio de Janeiro"
```

- Foco em arquivos de configuração
- **Tropeço**: tipo errado (ex: string sem aspas para número)

---

## 4. Diferenças sutis entre formatos

| Característica        | JSON | YAML | TOML | XML | CSV |
|-----------------------|------|------|------|-----|-----|
| Suporte a hierarquia  | Sim  | Sim  | Sim  | Sim | Não |
| Tipos primitivos      | Sim  | Sim  | Sim  | Não¹ | Não |
| Legível por humanos   | Médio | Alto | Alto | Baixo | Alto |
| Tamanho típico        | Médio | Médio | Médio | Grande | Pequeno |
| Comentários           | Não  | Sim   | Sim   | Não² | Não |

¹ XML só strings, tipos vêm de schema/XSD  
² Em XML comentários são possíveis mas não como metadados semânticos

---

## 5. Tropeços mais comuns (exemplos reais)

### Codificação de texto

- **CSV em Português**: usar UTF-8 ou Latin-1? Excel salva em ANSI por padrão
- **BOM no JSON** – quebra parsers antigos

### Delimitadores e escapes

- CSV com `"30,25"` dentro de campo → quebra linha
- JSON com `/` escapado desnecessariamente → `"http:\/\/site"`

### Indentação e espaços

- **YAML**: misturar TAB e espaço → erro obscuro
- **FWF**: `"João    "` vs `"João "` – muda tudo

### Vírgulas finais

- JSON: `[1,2,3,]` → erro (Python permite, JS não)

## 6. Bibliotecas no R

| Formato | Pacote principal                     | Exemplo de uso                             |
|---------|--------------------------------------|---------------------------------------------|

| JSON    | `jsonlite::fromJSON()`               | `lista <- fromJSON("arquivo.json")`        |
| YAML    | `yaml::yaml.load_file()`             | `config <- yaml.load_file("config.yml")`   |
| XML     | `xml2::read_xml()` + `xml_find_all()`| `doc <- read_xml("dados.xml")`             |
| TOML    | `RcppTOML::parseTOML()`              | `conf <- parseTOML("config.toml")`         |

## 7. Ferramentas Linux CLI

| Formato | Comando/filtro                     | Exemplo                                    |
|---------|------------------------------------|---------------------------------------------|
| CSV     | `csvkit` (`csvcut`, `csvgrep`), `mlr` (Miller) | `csvcut -c nome,idade arquivo.csv`        |
| FWF     | `awk` + substring                  | `awk '{print substr($0,1,10)}' dados.txt`  |
| JSON    | `jq`                               | `jq '.[] | {nome, idade}' dados.json`      |

| XML     | `xmlstarlet`                       | `xmlstarlet sel -t -v "//nome" dados.xml`  |
| TOML    | `tomlq` (do pacote `yj`)           | `tomlq '.pessoas.joao' config.toml`        |

pessoas:

### XML com erro (tag não fechada)

<pessoas>

</pessoas>
```

joao_idade = 30          # certo

## 10. Resumo e recomendações

| Se você precisa...                      | Escolha                     |
|-----------------------------------------|-----------------------------|
| Interoperabilidade web/API              | JSON                        |
| Configuração legível por humanos        | YAML ou TOML                |
| Máxima performance em big data          | CSV/FWF (com streaming)     |
| Documentos complexos com metadados      | XML (com schema)            |
| Dados tabulares simples                 | CSV (com `readr`/`fread`)   |

### Checklist de validação rápida

1. **Encoding** sempre UTF-8, exceto legado explícito
2. **Ferramentas CLI** (`jq`, `yq`, `csvlint`) salvam vidas
3. **Olhe o arquivo** no hexdump se der erro (`xxd arquivo | head`)

> Boa análise de dados começa com boa serialização – escolha o formato que equilibra legibilidade, ferramentas e robustez.

# 2. Dados estruturados vs não estruturados

Aqui vale usar contraste visual.

Pontos importantes:

# 3. Serialização e desserialização

Serializado em JSON:

Desserializado:
